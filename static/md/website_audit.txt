### #1 — Page Speed (Mobile & Desktop) ★
**Tool:** PageSpeed Insights API — `https://www.googleapis.com/pagespeedonline/v5/runPagespeed?url={clientURL}&strategy=mobile` + `&strategy=desktop`

**How it works (automated):**
The tool calls the PageSpeed Insights API for both mobile and desktop strategies automatically. It extracts the **Performance score** (0–100) for each and stores both values. Scoring is based on the lower of the two (mobile is almost always the limiting factor).

**Scoring logic:**

| Mobile Performance Score | Audit Score | Rating |
|---|---|---|
| 90–100 | 8–10 | 🟢 |
| 70–89 | 5–7 | 🟡 |
| Below 70 | 1–4 | 🔴 |

**Standard messages (auto-selected by tool):**

> 🟢 **Good:** Page speed is strong on both mobile (score: {mobile_score}) and desktop (score: {desktop_score}). No immediate action required, but monitor for regressions after new deployments.

> 🟡 **Needs attention:** Performance scores are in the acceptable range but not optimal — Mobile: {mobile_score}, Desktop: {desktop_score}. Common culprits: unoptimised images, render-blocking scripts, or lack of caching. Prioritised fixes are listed in the action plan.

> 🔴 **Critical:** Page speed is poor, especially on mobile (Mobile: {mobile_score}, Desktop: {desktop_score}). This directly impacts both user experience and Google rankings — Core Web Vitals failures can suppress search visibility. Immediate optimisation is required.

### #2 — Core Web Vitals (LCP, FID/INP, CLS) ◆
**Tool:** PageSpeed Insights API — same call as #1, extracts Core Web Vitals from the response

**How it works (automated):**
The PageSpeed API response includes Core Web Vitals data in the `loadingExperience` (field data from real users) or `lighthouseResult` (lab data) objects. The tool extracts all three metrics — **LCP**, **INP**, and **CLS** — and compares each against Google's defined thresholds. Score is calculated from how many metrics are in the "Good" band.

**Thresholds:**
- LCP: ≤2.5s = Good · ≤4.0s = Needs Improvement · >4.0s = Poor
- INP: ≤200ms = Good · ≤500ms = Needs Improvement · >500ms = Poor
- CLS: ≤0.1 = Good · ≤0.25 = Needs Improvement · >0.25 = Poor

**Scoring logic:**

| Passing metrics | Audit Score | Rating |
|---|---|---|
| All 3 pass ("Good") | 8–10 | 🟢 |
| 1–2 pass | 4–7 | 🟡 |
| 0 pass | 1–3 | 🔴 |

**Standard messages (auto-selected by tool):**

> 🟢 **Good:** All three Core Web Vitals pass Google's thresholds (LCP: {lcp}, INP: {inp}, CLS: {cls}). The site delivers a fast, stable, responsive experience. This is a direct ranking signal — maintain it.

> 🟡 **Needs attention:** {N} of 3 Core Web Vitals are outside the "Good" range (LCP: {lcp}, INP: {inp}, CLS: {cls}). The most common causes are slow LCP (large images or slow server response) and CLS (layout shifts from late-loading fonts or banners). Specific fixes are listed in the action plan.

> 🔴 **Critical:** Core Web Vitals are failing — {N} metrics are in the "Poor" range (LCP: {lcp}, INP: {inp}, CLS: {cls}). Google uses these as a direct ranking signal via the Page Experience update. This is a high-priority fix.

### #3 — Mobile Friendliness ★
**Tool:** Google Mobile-Friendly Test — `https://search.google.com/test/mobile-friendly?url={clientURL}`

**How to score:**
1. Run the URL through Google's Mobile-Friendly Test
2. Note whether it passes or fails, and read any specific issues flagged

| Result | Audit Score | Rating |
|---|---|---|
| Passes, no issues | 8–10 | 🟢 |
| Passes with minor warnings | 5–7 | 🟡 |
| Fails | 1–4 | 🔴 |

**Standard messages:**

> 🟢 **Good:** The page passes Google's mobile-friendliness test with no issues. Text is readable without zooming, tap targets are appropriately sized, and content fits the viewport.

> 🟡 **Needs attention:** The page passes the mobile-friendliness test but Google flagged some usability issues — typically small tap targets, text that requires zooming, or content slightly wider than the viewport. These are worth fixing but not critical.

> 🔴 **Critical:** The page fails Google's mobile-friendliness test. Given that Google indexes mobile-first, this is a significant issue affecting rankings and user experience on smartphones. Responsive design implementation is required.

### #4 — HTTPS & SSL Certificate ★
**Tool:** Auto — fetches URL and checks HTTPS status + certificate validity via `https://api.ssllabs.com/api/v3/`

**How it works (automated):**
The tool checks two things automatically:
1. Whether the URL redirects to HTTPS (not HTTP)
2. SSL Labs API call to check certificate validity, expiry date, and grade

**Scoring logic:**

| Condition | Score | Rating |
|---|---|---|
| HTTPS, valid cert, grade A/A+ | 9–10 | 🟢 |
| HTTPS, valid cert, grade B or warning | 6–8 | 🟡 |
| HTTP only, expired cert, or grade C/F | 1–4 | 🔴 |

**Standard messages (auto-selected by tool):**

> 🟢 **Good:** Site is fully served over HTTPS with a valid SSL certificate (Grade: {grade}, expires: {expiry_date}). No action required.

> 🟡 **Needs attention:** HTTPS is in place but the SSL configuration has weaknesses (Grade: {grade}). This may affect browser trust warnings or security posture. Review SSL Labs recommendations.

> 🔴 **Critical:** The site is not properly secured. Either it is served over HTTP, the certificate is expired, or it is invalid. Browsers display security warnings to users, and Google treats HTTPS as a ranking signal. This must be fixed immediately.

### #5 — XML Sitemap ★
**Tool:** Auto — fetches `{domain}/sitemap.xml` directly (and checks `robots.txt` for alternate sitemap location)

**How it works (automated):**
1. Fetches `{domain}/sitemap.xml`
2. Validates it is well-formed XML
3. Counts the number of URLs listed
4. **Fetches every URL listed in the sitemap and checks its HTTP status code** — flags any 4xx, 5xx, or redirect chains
5. Checks if the sitemap URL is declared in `robots.txt`

**Scoring logic:**

| Condition | Score | Rating |
|---|---|---|
| Found, valid XML, all URLs return 200 | 8–10 | 🟢 |
| Found, valid XML, some URLs have errors or redirects | 4–7 | 🟡 |
| Not found, malformed, or majority of URLs return errors | 1–3 | 🔴 |

**Standard messages (auto-selected by tool):**

> 🟢 **Good:** XML sitemap found at `{sitemap_url}`. Contains {url_count} URLs, all returning 200 OK. Sitemap is declared in robots.txt. Search engines can fully discover and crawl the site.

> 🟡 **Needs attention:** XML sitemap is present but {error_count} URLs return errors or are redirecting ({error_list}). These should be updated to their canonical final URLs. Serving stale or broken URLs in a sitemap wastes crawl budget.

> 🔴 **Critical:** No XML sitemap found at the expected location. Without a sitemap, search engines rely entirely on link discovery to find pages — this is unreliable, especially for newer or larger sites. A sitemap should be created and submitted in Google Search Console.

### #6 — Robots.txt ★
**Tool:** Auto — fetches `{domain}/robots.txt` directly

**How it works (automated):**
1. Fetches `{domain}/robots.txt` and confirms it returns HTTP 200
2. Parses for: `Disallow` rules (especially `/` blocking all), `Allow` rules, `Sitemap` declaration, and `User-agent` directives
3. Flags if critical paths (e.g. homepage, key service pages) are blocked

**Scoring logic:**

| Condition | Score | Rating |
|---|---|---|
| Found, no critical blocks, sitemap declared | 8–10 | 🟢 |
| Found, minor issues or missing sitemap declaration | 5–7 | 🟡 |
| Not found, returns 404/500, or blocks all crawling | 1–4 | 🔴 |

**Standard messages (auto-selected by tool):**

> 🟢 **Good:** robots.txt is present and correctly configured. No critical paths are blocked from crawling. Sitemap location is declared.

> 🟡 **Needs attention:** robots.txt is present but has minor issues — {specific_issue}. This is not critical but should be reviewed to avoid accidental crawl restrictions.

> 🔴 **Critical:** {one of the following} — robots.txt is missing (returns 404), which means crawlers receive no directives and may index unwanted content. / robots.txt contains `Disallow: /` which is blocking all search engine crawling. This would prevent the site from appearing in search results entirely. This must be fixed immediately.

### #7 — Canonical Tags ★

**How it works:**
Fetch the homepage and all URLs from the sitemap. For each page, check:
1. Presence of `<link rel="canonical" href="...">` in the `<head>`
2. Whether the canonical points to itself (correct) or a different URL (potential issue)
3. Whether canonical URLs are absolute (not relative)
4. Consistency across paginated pages (if applicable)
5. HTTPS and trailing slash consistency

**Scoring logic:**

| Condition | Score | Rating |
|---|---|---|
| Canonical present, self-referencing, absolute URL, consistent | 8–10 | 🟢 |
| Canonical present but some pages inconsistent or using relative URLs | 5–7 | 🟡 |
| Canonical missing on multiple pages, or canonicals pointing to wrong URLs | 1–4 | 🔴 |

**Standard messages (AI-generated, edited as needed):**

> 🟢 **Good:** Canonical tags are correctly implemented across all crawled pages. Each page points to its own canonical URL, preventing duplicate content signals from reaching Google.

> 🟡 **Needs attention:** Canonical tags are present on most pages but inconsistencies were found: {specific_issues}. While not critical, these can cause mixed signals to search engines about which version of a page to index.

> 🔴 **Critical:** Canonical tags are missing from multiple key pages. Without canonicals, Google may choose any version of a page to index (HTTP vs HTTPS, trailing slash vs not, www vs non-www), potentially splitting ranking signals across duplicates.

### #8 — Structured Data / Schema ★

**How it works**
Parse all JSON-LD blocks from fetched pages and evaluate:
1. Schema type present (e.g. `Organization`, `LocalBusiness`, `Article`, `Product`, `BreadcrumbList`, `FAQPage`)
2. Required fields present for each type (per schema.org spec)
3. Whether schema is appropriate for the page type
4. No critical errors (missing `@context`, wrong types)

**Scoring logic:**

| Condition | Score | Rating |
|---|---|---|
| Relevant schema present, all required fields, no errors | 8–10 | 🟢 |
| Schema present but incomplete fields or suboptimal type | 5–7 | 🟡 |
| No schema, or schema with critical errors | 1–4 | 🔴 |

**Standard messages:**

> 🟢 **Good:** Structured data is correctly implemented. {schema_types} schema found with all required fields present. Rich result eligibility confirmed. This improves how Google displays the site in search results.

> 🟡 **Needs attention:** Schema markup is present but incomplete. {specific_issues}. Incomplete schema rarely breaks rich results but misses the opportunity for enhanced SERP display.

> 🔴 **Critical:** No structured data found on key pages. Implementing schema — at minimum `Organization` and relevant page-type schema — would improve Google's understanding of the site and enable rich result eligibility.

| Minor indexing issues, few excluded pages | 5–7 | 🟡 |
| Significant crawl errors, important pages not indexed | 1–4 | 🔴 |

**Standard messages:**

> 🟢 **Good:** Index coverage looks healthy. All key pages are indexed and no significant crawl errors were found in Google Search Console.

> 🟡 **Needs attention:** {N} pages are excluded from the index. The most common reasons are: {reason_from_GSC}. Review these exclusions — some may be intentional (thank you pages, admin areas) but others may indicate crawlability issues.

> 🔴 **Critical:** Significant indexing problems found. {N} important pages are not being indexed due to {primary_reason}. This directly limits search visibility — pages Google can't index can't rank.

> 🟡 **Needs attention:** {N} redirect chains were found. Each additional hop in a chain dilutes link equity and slows page load. These should be updated to point directly to the final URL.

> 🔴 **Critical:** Broken links (4xx errors) found on {pages}. These create dead ends for both users and crawlers, wasting crawl budget and damaging user experience. Additionally, {N} redirect chains need to be resolved.

**Standard messages:**

> 🟢 **Good:** No significant duplicate content or thin pages detected. Each page appears to carry unique, substantive content that serves a distinct purpose.

> 🔴 **Critical:** Significant duplicate or thin content found. {N} pages have fewer than 300 words of substantive content, and/or multiple pages are competing for the same keyword intent. This dilutes the site's authority and confuses search engines about which page to rank.

### #12 — Hreflang (Multilingual) ◆

**How it works:**
Check for `<link rel="alternate" hreflang="...">` tags across all crawled pages and validate:
1. Presence and correct language/region codes (e.g. `en-GB`, `fr-FR`)
2. Reciprocal hreflang pairs (page A points to B, B points back to A)
3. `x-default` tag present
4. Self-referencing hreflang for the current page's language
5. No broken hreflang URLs

**Scoring logic:**

| Condition | Score | Rating |
|---|---|---|
| Not applicable (monolingual site) | N/A | N/A |
| Present, all reciprocal, x-default set, no broken URLs | 8–10 | 🟢 |
| Present but missing reciprocals or x-default | 5–7 | 🟡 |
| Present but critically broken, or missing on multilingual site | 1–4 | 🔴 |

**Standard messages:**

> 🟢 **Good:** Hreflang is correctly implemented across all language variants. Reciprocal tags are in place and `x-default` is set. Google can correctly serve the right language version to the right audience.

> 🟡 **Needs attention:** Hreflang tags are present but {issue} — e.g., missing reciprocal references or `x-default` not set. These errors won't cause immediate harm but can result in the wrong language version being served in some regions.

> 🔴 **Critical:** The site has multiple language versions but hreflang is {missing / critically misconfigured}. Without correct implementation, Google may serve the wrong language to international visitors and duplicate content penalties can occur.

> ℹ️ **N/A:** The site is monolingual — hreflang is not applicable.

**Standard messages:**

> 🟢 **Good:** Heading structure is logical and well-optimised. Each page has a single H1 containing the primary keyword, with H2/H3 subheadings used to organise content and support topical coverage.

> 🟡 **Needs attention:** {specific_issue} — e.g., the H1 on {page} doesn't include the target keyword, or H2s are used before an H1 is established. Headings are a clear on-page signal — small improvements here have reliable impact.

> 🔴 **Critical:** Heading structure is significantly broken on multiple pages: {specific_issues}. Missing or incorrect H1 tags in particular directly impact how Google determines a page's primary topic.

| Condition | Score | Rating |
|---|---|---|
| Ranking for 20+ relevant keywords, several on page 1 | 8–10 | 🟢 |
| Ranking for 5–20 keywords, mostly page 2–3 | 5–7 | 🟡 |
| Fewer than 5 keywords, no page 1 visibility | 1–4 | 🔴 |

### #49 — Answer-Ready Content Structure ◆

### #52 — AI Crawler Access & llms.txt ★
**Tool:** Direct fetch — `{domain}/robots.txt` and `{domain}/llms.txt`

**How to check:**
1. Open `{domain}/robots.txt` and check the directives for AI crawler user-agents: `GPTBot`, `OAI-SearchBot`, `ClaudeBot`, `PerplexityBot`, `Google-Extended`, `CCBot`, `Bytespider`
2. Determine whether any are blocked, and whether that block is **intentional** (a deliberate content-protection decision) or **accidental** (a blanket rule that is silently removing the site from AI answers)
3. Check for the presence of an `llms.txt` file (an emerging convention for guiding LLMs to key content)
4. Flag the common failure mode: a site that *wants* AI visibility but is inadvertently blocking the crawlers that would provide it

**How to score:**

| Condition | Score | Rating |
|---|---|---|
| AI crawlers permitted (or blocked by clear intent); access aligned with goals | 8–10 | 🟢 |
| Mixed/unclear directives, or no consideration given either way | 5–7 | 🟡 |
| AI crawlers accidentally blocked while AI visibility is a goal | 1–4 | 🔴 |

**Standard messages:**

> 🟢 **Good:** AI crawler access is aligned with the client's goals — the relevant user-agents are permitted (or blocked by deliberate choice), so nothing is silently working against the site's AI visibility. {llms_txt_note}

> 🟡 **Needs attention:** The `robots.txt` directives around AI crawlers are unclear or haven't been considered. {specific_issue}. It's worth making a deliberate decision here — either open access to support AI visibility, or restrict it as a conscious content-protection choice — rather than leaving it to a legacy blanket rule. An `llms.txt` file could also be added to guide engines to the key pages.

> 🔴 **Critical:** The site is accidentally blocking AI crawlers ({blocked_agents}) even though AI visibility is a stated goal. This directly prevents the site from appearing in the answer engines that rely on those crawlers. Correcting the `robots.txt` rules is a fast, high-leverage fix.
